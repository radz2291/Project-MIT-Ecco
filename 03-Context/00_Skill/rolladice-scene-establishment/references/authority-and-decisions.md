# Authority, Decisions and Safe Autonomy

## One source owns each kind of truth

Start with project instructions and its current authority map. Read the original engineering source or client comment when a dispute depends on its wording. Do not replace it with the most recent assistant summary. Resolve contradictory sources explicitly with the appropriate owner.

Distinguish permission from truth. A director may authorize an illustrative example without making it measured data. An engineering source may establish a mechanism without giving permission to publish a confidential log. A successful export proves file creation, not correctness or client approval.

| Source | Governs | Does not establish by itself |
|---|---|---|
| Domain evidence, measured data, verified CAD | Physical/data meaning and constraints | Aesthetic choices or publication rights |
| Client/contract/brand requirements | Agreed scope, required copy, identity and restrictions | Unstated performance claims |
| Current owner decisions | Creative selection and authorized work scope | Engineering certification or third-party rights |
| Narrative plan | Ordered audience discoveries | Exact camera coordinates or dimensions |
| Taste evidence and references | Contextual visual preference | A universal look for every future scene |
| Inspected scene and test results | Actual implementation, coordinates and observed behavior | The scientific validity of an illustrative dataset |
| Agent report | What the agent says it checked | Independent verification by the reviewer |

## Keep four kinds of status separate

Do not make one tag do four jobs.

**Evidence kind:** measured/observed, derived, simulated, operational state, illustrative, or interpretation. "Derived" means computed from identified inputs. "Illustrative" means deliberately made for explanation.

**Verification:** inspected directly, source-supported, agent-reported, or unverified. Name the actual evidence. A frame may support appearance while leaving shader independence unverified.

**Decision:** accepted, experimental, unresolved, superseded or rejected. Record who decided, for which version, and for what scope.

**Rights:** cleared for this use, restricted, or unknown. A screenshot supplied for review is not automatically approved for public release. Do not copy restricted images into reusable skill packages.

Example: an amplitude image can be illustrative, mapping-verified, visually accepted, and restricted to internal review. None of those labels changes the others.

## Approval scope

Record approval as: **decision + artifact/version + owner + allowed action + conditions + unaffected work**.

"The texture is approved" permits the accepted texture treatment; it does not certify sensor resolution, approve all camera views or release a whole sequence. "Proceed with integration after the seam check passes" does authorize that integration once the named condition is verified, assuming current project rules allow it. Do not ask again by habit.

A full release must say whether it covers a proof, scene build, integration, finishing, export, commit or publication. Never infer permission for a destructive action or public disclosure from an aesthetic approval.

## Autonomy boundaries

**Fixed:** authoritative geometry/data, known physical relationships, client constraints, accepted scene meaning, selected representation, source identity and delivery bounds.

**Free within scope:** implementation techniques, rig/node structure, inexpensive testing method, minor composition adjustments that preserve the approved views, file organization following project rules, and performance optimization that does not weaken the required proof.

**Must return for a decision:** changing the story, replacing a selected look, materially changing dimensions or data, adding a stronger technical claim, changing an accepted continuity strategy, altering shared masters, exceeding a budget, or integrating when only a test was authorized.

The same Codex agent can switch between director and executor roles. Make the role and permission clear instead of spawning extra agents. Do not convert direct user feedback into a hidden production change: first state the affected decision, then act only within the actual instruction.

## Version and change discipline

On new feedback:

1. Capture the exact new requirement and what it supersedes.
2. Identify its owning stage and the dependent assets, labels, tests and neighboring shots.
3. Preserve unaffected accepted decisions and previous candidates.
4. Make the smallest permitted revision or propose a better concept when the old one is failing.
5. Recheck only affected acceptance criteria, plus the joins that can break.
6. Update the existing contract and records if writes are authorized.

A newer candidate can be rejected while older geometry remains the working baseline. Never return to a previously rejected design merely because it is easier to implement.

A changed source dataset invalidates its displayed evidence and any claims tied to it. It does not automatically invalidate the camera rhythm. A new camera can invalidate texture readability without invalidating UV mapping. These distinctions prevent full-project resets.

## Continuity without false identity

Record whether adjacent scenes share the same physical event, same object, same dataset, or only a conceptual connection. Their cameras and environments may differ.

A lateral motion-matched cut can connect independent scene files. Match apparent screen movement and attention rather than copying world transforms blindly. However, do not suggest two different illustrative wall profiles are the exact same recorded interval. Reconcile the data or establish a clear explanatory change.

## Files, privacy and recovery

Keep an approved baseline, a working candidate and an evidence path distinguishable. Reuse the project's structure; do not mandate new folder trees in every scene. Preserve originals and identify modified derivatives. Store portable relative paths where supported, and verify assets survive reopening.

A Windows file link is not readable from a remote chat runtime. A chat `/mnt/data` attachment is not necessarily on the executor's machine. Verify actual access instead of inventing paths or a completed inspection.

Do not overwrite unsaved live application work. Inspect in a separate process/version when necessary. Use the project's Git integrator and preserve unrelated changes. No force-push, deletion, task mutation or public media upload is granted by this skill.

## Reusable versus project-specific knowledge

Transfer the method: clear comparisons, data provenance, cause-and-response, scoped proof and useful camera arrivals. Keep client dimensions, sensor counts, palette meanings, tool settings, render budgets and brand assets in project sources.

Do not turn "this larger pixel treatment works here" into a universal rule that scientific data must look pixelated. Do not turn "use an orbit here" into a house camera preset.
