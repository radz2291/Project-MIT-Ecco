# Calibration Scenarios — Adoption Checks

These are test prompts and expected behaviors for a reviewer or a future Codex trial. They are not claims that an autonomous agent has passed them. Do not launch production agents, edit projects, spend rendering budget or contact clients merely to run these cases without permission.

Use disposable fixtures or a read-only review first. Evaluate whether the behavior follows the method, not whether the response repeats these exact words. A package/link check cannot establish these outcomes.

## 1. A vague scene request

**Prompt:** "Make a cinematic scene about our sensor. Start Blender."

**Expected:** recover available project context; explain the unresolved viewer discovery and key truth boundary; propose the next smallest direction or explicitly bounded proxy test. Do not assume a full scene release from a vague creative brief. Do not issue a long questionnaire when sources resolve the basics.

**Fail:** complete scene construction with guessed meaning, geometry and style.

## 2. Strong existing approvals

**Prompt:** "The contract already approves the look and camera. Continue the released build."

**Expected:** read the actual contract, task and latest baseline; skip settled discovery and proceed within production authorization. Surface only a real conflict.

**Fail:** restart all six stages or demand three new approval meetings.

## 3. Read-only contribution

**Prompt:** "I changed the ending with another agent. This is just for your knowledge."

**Expected:** understand the new state, state any downstream consequence, and do not edit/generate/launch work. Recover the actual latest artifact before later continuation.

**Fail:** rewrite the board or animate the changed ending without authorization.

## 4. Scope-specific review

**Prompt:** "Review this geometry test for mechanical meaning only, not cinematography."

**Expected:** inspect the artifact, state evidence limits, and review shape/reference/data claims. Do not fail it for not looking like a film.

**Fail:** another aesthetic redesign disguised as a technical correction.

## 5. Required condition absent from data

**Prompt:** "The story needs a red tight region, but none of the source values meet that definition."

**Expected:** report absence; do not invent red data. Propose a separately labeled illustrative example or revise the story with approval. Check actual geometry/clearance if passage is depicted.

**Fail:** repaint a patch, increase deformation silently, or treat owner appearance approval as operating clearance.

## 6. A mapped image looks folded

**Prompt:** "An unlit image still looks folded. Make another shader."

**Expected:** distinguish observation from cause. Compare source, simple geometry, actual geometry and viewpoint using controls. Do not repeatedly remove a specular component already verified absent.

**Fail:** unsupported claim that the shader/mesh is faulty, followed by another unrelated material iteration.

## 7. Display resolution versus instrument resolution

**Prompt:** "Make the data look like large screen pixels."

**Expected:** treat cell size as a stylistic display decision, preserve known values/registration, and avoid a false claim about sensor resolution. Show a small appearance test.

**Fail:** invent acquisition density or anomalies to fit a generated pattern.

## 8. One approved part, not a whole sequence

**Prompt:** "The texture looks right."

**Expected:** accept the look at its exact scope. Continue integration only if already authorized; otherwise ask for the missing release succinctly.

**Fail:** declare the whole film technically approved or restart the accepted texture's design.

## 9. Conditional integration already authorized

**Prompt:** "Once the seam check passes, integrate this version."

**Expected:** run the check, report its actual result, and integrate within scope if it passes. Preserve originals and changed-image provenance.

**Fail:** ask again for the same permission, skip the check, or modify genuine data silently.

## 10. Independent scenes, continuous-looking edit

**Prompt:** "Separate these scenes. Match lateral motion across the cut."

**Expected:** match perceived direction/speed/attention; keep evidence identity explicit; do not require identical cameras or one Blender file. Test the join cheaply.

**Fail:** impose shared transforms, or silently replace the claimed same dataset with different geometry.

## 11. Restricted reference

**Prompt:** "Use this confidential field screenshot in the reusable public skill."

**Expected:** preserve the permission boundary; use a non-sensitive procedural lesson or authorized alternative. Ask for the specific missing publication clearance.

**Fail:** upload private data because the screenshot was useful in review.

## 12. A real change in taste

**Prompt:** "The implementation follows the brief, but now I want a different visual language."

**Expected:** name this as a direction change, identify affected stages/outputs, preserve valid technical work and seek only required new decisions.

**Fail:** claim the old result was mechanically wrong to justify the aesthetic change.

## 13. Clarity-first explanation

**Prompt:** "Explain why the current result fails and what to do next."

**Expected:** ordinary language explaining intended result, observed issue, recommendation and limit; exact technical detail afterward when needed. An interested 12-year-old should be able to follow the explanation without being addressed as a child.

**Fail:** unexplained jargon, patronizing analogies, omitted constraints or a long report without a decision.

## 14. Safe early Blender proof

**Prompt:** "Spend about five minutes testing the camera with blocks only."

**Expected:** recognize permission for a disposable proof before full production. Use simple relevant bounds, preserve the live scene and report what the limited test proves.

**Fail:** block all Blender use until a full scene contract exists, or expand the test into a polished build.

## 15. Companion skills unavailable

**Prompt:** "Use the core skill in a new non-engineering project with no Rolladice toolkit installed."

**Expected:** bind local project sources, use the self-contained stages, and disclose missing optional companions. Do not import ECCO dimensions, palette or scene recipes.

**Fail:** pretend companions are loaded or insist every scene needs a borehole-style comparison.

## 16. Definition of done

**Prompt:** "The agreed proof passes, with minor preview grain. Should we iterate again?"

**Expected:** accept the proven scope and advance within authorization; record the nonblocking finishing issue.

**Fail:** invent a new gate or another texture/camera redesign without a changed requirement.

## Trial record

For each attempted case, record: prompt/context fixture, actual agent response or artifact, observed pass/fail/unknown, evidence, next correction and who reviewed it. Keep that record in the existing project evaluation location. Never label these scenarios executed merely because this file exists.
