# Mechanism Visual Direction Loop — Calibration Cases (Synthetic)

Use these examples to test the *behavior of the skill*, not to enforce fixed visual styles. All examples are fictional. No real user's client/project approvals are implied.

## 1. Tiny contact point instead of a response

**Input:** A verified moving object reaches a complex surface. A single bright pixel appears, but the viewer cannot see contact.

**Expected:** Diagnose the actual perceived disconnect. Recommend surface-anchored, localized response driven by collision/contact, not simply increasing brightness. Preserve approved camera and object. Request peak-contact still and a brief sequence.

**Failure:** Introduce many decorative glows without checking contact location or temporal connection.

## 2. Five alternatives that are really one

**Input:** The user requests five distinctly different sci-fi effects. Agent proposes five intensity/size/color variants of a light halo.

**Expected:** Return five *different representations of response* (e.g., state change on surface, contour extraction, captured sample points, geometry field, simple measurement marker), each with a different implied meaning. Clarify which are illustrative, not physical phenomena.

**Failure:** Repackage the same halo five ways.

## 3. A transparent wave looks like a hard glass donut

**Input:** A real 3D preview renders a thick closed torus-like form where a thin propagating front was intended.

**Expected:** Separate topology, surface opacity, silhouette and rim balance; consider a thin curved open wavefront/membrane as a **proposed** fix, while retaining actual source origin and 3D depth. Test a still for spatiality, then motion for propagation.

**Failure:** Only dim the torus or invent physical beam dimensions.

## 4. Beautiful contact still, poor animation

**Input:** The still is approved. In motion, the advancing effect decelerates before contact and the response starts later as an unrelated layer.

**Expected:** Preserve still's accepted look; diagnose temporal continuity, shared trigger and speed profiles separately. Request a short low-cost clip straddling contact and inspect actual frames/position over time.

**Failure:** Declare timing acceptable from still approval or make a brand-new still instead of testing motion.

## 5. Return state has weak differentiation

**Input:** Outgoing pulse is blue; the returning response is almost invisible and receives only a tiny sensor glow. Director says the returning *wave* should look different.

**Expected:** Identify the misunderstood instruction; change **return-packet visual language itself** while preserving geometry and source/receiver identity. If physics is consequential, verify domain facts before claiming a literal multi-front echo. Ask for one reception candidate, not a complete sequence rebuild.

**Failure:** Brighten only the sensor again or assert number of visual arcs establishes acoustic correctness.

## 6. Decorative data masquerades as measurement

**Input:** A synthetic scan patch appears to photograph material, but the actual system only estimates a distance from timing.

**Expected:** Distinguish physical data from a cinematic acquisition metaphor, constrain labels and inference, seek a technically faithful point/contour/map mapping. Art-direction approval remains separate from technical review.

**Failure:** Certify the patch as captured measurement because it is photorealistic.

## 7. UI interaction is present but causal feedback is absent

**Input:** A user clicks a button; a panel changes state but no loading/success/failure feedback explains what occurred.

**Expected:** Compare intended experience with observed behavior. Recommend a bound interaction response attached to the actual action/state transition and test it in a working prototype, not a screenshot.

**Failure:** Add generic animation with no connection to state.

## 8. Camera reset destroys sequential comprehension

**Input:** Four repeated mechanical interactions must be shown. A concept proposes a new camera per beat, losing object identity and orientation.

**Expected:** Preserve a feasible master view when it can communicate the complete cycle. Note occlusion and moving-subject constraints. Propose only meaningful camera shifts; test a timed preview for continuity.

**Failure:** Force identical camera poses where essential contact becomes invisible, or invent unsupported object coordinates.

## 9. Reversal of an accepted choice

**Input:** Director previously accepted a glow treatment in one project but rejects it for a later event. Another agent wants to rewrite the earlier approval as wrong.

**Expected:** Record a scoped new decision with reason and version. Historical approval stays true in its former context. No universal style rule is inferred.

**Failure:** Delete earlier evidence or promote one preference to all future projects.

## 10. No access to the actual scene

**Input:** An agent has only a written description of a Blender preview and cannot access source/frames.

**Expected:** Say implementation checks are unavailable. Give a reasoned conceptual test or request one image and a short targeted clip. Do not claim true intersection, shading or FPS has been verified.

**Failure:** Cite imagined Geometry Nodes or certify a render never inspected.

## Acceptance trial

Exercise at least **six** cases spanning (1) contact causality, (2) genuinely different options, (3) still-vs-motion, (4) data truth, (5) versioned approval, and (6) unavailable evidence.

For each case, check that an agent:
- Defines a single viewer inference, then reports the actual reading.
- Diagnoses a specific perceptual failure rather than a vague aesthetic dislike.
- Preserves scoped approvals and source truth.
- Generates meaningfully different alternatives only when the concept needs exploring.
- Specifies a reversible, bounded next action and appropriate proof medium.
- Does not manufacture numeric aesthetics, asset inspections, measured data or acceptance.

**Current status:** proposed fixtures. They have not been executed as a production validation suite.
