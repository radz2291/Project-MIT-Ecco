# Mechanism Visual Direction Loop

Direct the **meaning of an interaction** using the **actual artifact**, then improve it with the smallest useful experiment. The core loop is:

**See → Interpret → Diagnose → Redirect → Inspect.**

This is one skill unifying reality-grounded human–AI co-direction, cause-and-response effect conception, and surgical visual critique. It is **not** a universal aesthetic recipe, a physics solver, a camera preset, or an implementation framework.

## What this skill owns

- **Own:** reviewing a specific visible mechanism beat; describing what the viewer currently perceives; diagnosing the gap between intended and perceived causality; exploring genuinely different visual-response concepts when needed; prescribing bounded changes; testing whether the new artifact communicates better; recording a scoped decision.
- **Does not own:** factual/engineering certification, new personal taste discovery, entire narrative or camera design, motion-system construction, final rendering, or automated client approval. Use the target project's authoritative sources and existing contracts; do not create duplicate governance.
- **Coordinate with:** contextual-aesthetic-judgment for competing taste choices, information-to-visual-storytelling for truthful measurement/data meaning, spatial-storytelling-camera-choreography for a substantial camera/motion redesign, and creative-knowledge-to-execution-engineering for complex formal agent handoffs. Load only when needed.
- **No house style:** Never import a specific client, artist, color palette, shape, waveform, or material into another project. Transfer the *diagnostic method*.

## Choose the next honest mode

- **Inspect/review:** a real still, playblast, UI state, frame sequence or scene is provided. Judge what is **actually visible**; label code/physics/timing/hidden frames unverified unless inspected.
- **Explore:** the intended effect is unclear or a selected approach is fundamentally weak. Propose **meaningfully different effect mechanisms**, not superficial variations in glow/brightness.
- **Refine:** a direction is chosen and works in principle. Preserve accepted anchors and make the smallest correction necessary.
- **Handoff:** the user wants instructions for a Blender, Houdini, Unreal, UI, motion, or other execution agent. Translate the confirmed visual goal into testable effect behavior; leave the implementation architecture negotiable unless supplied.
- **Continue:** after a new artifact arrives, compare it with the previous exact candidate and advance the same decision; do not restart ideation by habit.

When the actual frame is absent, inspect available source/scene evidence or ask for one representative frame; do **not** claim to have visually verified unseen output. A concept study may still proceed clearly marked as provisional. Do not ask for a full brief if a reversible next test is possible.

## The operating loop

### 1. SEE — Anchor in reality and preserve decisions

Inspect the candidate at the resolution/length needed for this decision. Collect only the essential context:

- **Exact artifact** and version/frame/time; whether a still, motion preview, diagram, screenshot, reference image or real implementation.
- **Viewer goal** and causal moment the artifact must communicate.
- **Physical/data authority:** authentic geometry, timing, interaction, signal, data, or source rules; what is measured, inferred, simulated, illustrative, or unknown.
- **Existing approvals:** what is accepted, by whom, at which scope; what is only proposed or historically rejected.
- **Feasibility:** actual depth/occlusion, sizes, adjacency, anchors, camera, performance and tool limitations, when inspectable.

Generated concept art is helpful for appearance but is not evidence that the real project geometry allows it. If a previously approved treatment conflicts with real geometry, expose the conflict rather than hiding it.

### 2. INTERPRET — State the viewer's experience, not a tool operation

Complete two sentences:

- **Intended:** "The viewer should understand/feel ___ because they see [cause] lead to [response] and then [consequence]."
- **Observed:** "Right now, the frame/clip instead reads as ___."

Identify the **decision unit** (one contact, one return, one transform, one measurement reveal, one transition), not the entire film or product. Separate a physical event from its visualization and from any derived information. A bright surface does not by itself prove contact; a digital-looking patch does not by itself mean measurement.

For effects, draw the minimum causal chain:

`origin → propagation/action → encounter/trigger → response → persistence/fade → resulting information or state`

A beat may omit stages when the story does not require them. A static candidate may validate a visible state but cannot establish actual timing or direction of travel.

### 3. DIAGNOSE — Name the perceptual failure and plausible cause

Compare what was meant with what is seen. Pick the **one highest-leverage failure** first:

| Failure family | What the viewer misreads | What to inspect |
|---|---|---|
| **Contact / anchoring** | A dot, gap or sticker instead of a real interaction | Actual intersection, coordinate space, surface normals, depth |
| **Shape / material** | A wave looks like a donut, rigid object or smoke | Topology, silhouette, thickness, facing opacity, edge balance |
| **Cause / response** | Result seems to switch on independently of its trigger | Shared spatial driver, trigger order, response growth |
| **Hierarchy / distinction** | Return, reaction, or outcome is lost behind the stimulus | Contrast, color encoding, screen-space size, spatial separation |
| **Temporal behavior** | Motion pauses, accelerates unnaturally or breaks continuity | Position-versus-time, propagation speed, overlaps, holds |
| **Information meaning** | A decorative effect looks like literal recorded data | Provenance, symbols, units, source/result mapping |
| **Continuity** | The next still/shot changes perspective or effect rules unnecessarily | Stable assets/camera, anchors, accepted color and behavior |
| **Feasibility / truth** | Attractive concept cannot fit real geometry or implies a false mechanism | Source files, evaluated scene, validated data, technical review |

State the issue as **specific unwanted perception → likely cause → consequence for comprehension**. Treat a screenshot diagnosis as a **hypothesis** about geometry/shader logic, not proof of unseen nodes. Avoid arbitrary aesthetic scores, fake precision and generalized "make it more cinematic."

### 4. REDIRECT — Select the right scale of change

**If the concept is failing:** explore a small set of *genuinely different response mechanisms*. For example, instead of five brighter contact glows, compare a surface-state transformation, a geometry trace, a temporary particle capture, a contour reveal, and a clean no-effect measurement marker. Vary *what happens* and what the viewer infers. Include a quiet/simple solution when it may be stronger. If the user requests five, make all five conceptually distinct.

**If the concept works:** fix the limiting mechanism, not the whole composition. Split the handoff into:

- **PRESERVE (locked):** exact approved camera/asset/state, meaningful treatment, versions, factual invariants.
- **CHANGE (bounded):** precise visual cause, trigger, appearance, interaction, envelope or motion to improve.
- **FREE (executor discretion):** shader/node topology, rigging, procedural setup, exact parameters after scene inspection.
- **DO NOT IMPLY:** false quantities, unsupported material behaviors, impossible geometry, an independently measured digital image, unearned approval.
- **NEXT PROOF:** one still or short motion study at the critical event with a clear pass/fail question.

Match the review to the medium. A proposed generated reference is not a locked engineering source or automatic first/last video anchor. Use it only if it resolves a decision more cheaply than building the effect.

### 5. INSPECT — Evaluate the new artifact against the *same* claim

On the next version ask:

1. Can a viewer read the **cause before the response** without explanatory text?
2. Does the response appear at the **correct real object/location** and obey project-specific physical/data limits?
3. Is the resulting change obvious enough to matter, without spectacle drowning the subject?
4. Are approved features preserved and previously rejected failures absent?
5. Does the candidate work at intended scale and playback speed, not only in a zoomed still?
6. Are temporal continuity and actual tool behavior verified by *motion* or runtime evidence rather than a frame?
7. What was physically inspected, what was self-checked, and what still awaits user or domain approval?

Report **better / still failing / different failure**, cite the actual candidate version, and identify the single next bounded step. If the selected direction now works, **stop reopening it** and advance to the next causal beat. If repeated local tweaks fail, step back to a different effect concept instead of escalating glow, complexity and revision count indefinitely.

## Response and agent-handoff shapes

**Quick creative review (default, concise):**
1. **Verdict:** works / partially works / not yet; specify *visible* scope.
2. **Reads as:** current perception contrasted with intended meaning.
3. **Preserve:** 2–4 approved elements.
4. **Change:** one prioritized correction and why.
5. **Next output:** exact still/seconds/interaction to inspect and one acceptance question.

**Exploration:** 3–5 truly different effect concepts, each with viewer meaning, spatial behavior, implementation risk, and where it fails; recommend one but let the owner choose.

**Execution feedback:** use [review-note template](references/review-note-template.md), adapting to an existing ticket/comment/scene contract instead of creating another parallel authority document. Specify the latest approved source and whether edits are authorized. Never invent a successful update, render, push, or approval.

**Optional calibration:** [cross-domain cases](references/calibration-cases.md) test whether an agent actually follows this loop. These are synthetic examples, not evidence of production validation.

## Guardrails and stop rules

- **Truth outranks spectacle.** If a contact graphic is a metaphor for sampling, say so; do not present it as literal captured texture or scientific proof.
- **One approval has one scope.** A choice of effect language is not approval of Blender implementation, animation, engineering, all shots or delivery.
- **Do not double-book responsibility.** A director judges visual meaning; the execution agent controls implementational details and performs actual tests; the designated human/domain reviewer accepts what they are authorized to accept.
- **Honor revisions.** Preserve accepted and rejected candidates with identifiers; do not silently replace the source of truth or rerun accepted exploration without a meaningful new problem.
- **Keep user effort low.** Make the strongest safe recommendation and continue bounded work; ask one focused question only at a genuine creative fork, unavailable critical reference, or authority boundary.
- **No false persistence.** Save approved direction and tests to existing project records only when requested/authorized; otherwise deliver the guidance directly in chat.

## Self-check

- Was the **actual frame or clip** inspected or clearly marked unavailable?
- Can I state intended vs observed meaning in plain words?
- Did I distinguish real cause/effect from artistic representation?
- Were requested alternatives meaningfully different rather than five variations of one glow?
- Did I protect valid work and propose the smallest productive change?
- Does my next test observe the property I claim to assess?
- Can the next agent execute the correction without inheriting one project's aesthetics?
- Is approval recorded only for the exact candidate and scope?

**Skill maturity:** v0.1 / authored for trial. Documentation and structural checks are not proof of cross-domain agent performance.
